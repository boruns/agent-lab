# 第 2 课：工具契约与安全执行

## 本课要解决的问题

第 1 课中，Agent 已经能让模型选择一个工具。但 `RecordingTool` 只是测试替身，并没有真正
处理外部输入。现在我们要实现第一个真实工具：安全计算器。

为什么不直接让模型自己计算？

- 模型生成文本，不保证算术结果始终准确；
- 工具可以提供确定性结果，相同输入得到相同输出；
- Agent 的价值之一，就是知道什么时候应把任务交给更可靠的外部能力。

## 1. 工具是什么

在本项目中，工具是 Agent 被允许调用的一项能力。它至少需要：

```text
name         模型请求工具时使用的稳定标识
description  告诉模型这个工具解决什么问题
run          主程序实际执行能力的入口
```

`CalculatorTool` 不需要继承 `Tool`。Python 的 `Protocol` 使用结构化类型：只要对象具有
兼容的 `name`、`description` 和 `run()`，就满足工具协议。

## 2. 为什么工具输入不可信

模型会生成类似这样的调用：

```python
ToolCall("calculator", {"expression": "6 * 7"})
```

但它也可能因为误解、提示注入或攻击内容而生成：

```python
ToolCall(
    "calculator",
    {"expression": "__import__('os').system('危险命令')"},
)
```

模型不是安全边界。工具必须自己校验参数和允许的操作，即使 Prompt 已经告诉模型不要做危险
操作，也不能省略程序校验。

## 3. 为什么不能使用 `eval()`

`eval()` 执行的是 Python 表达式，不只是数学表达式。直接把模型输出交给 `eval()`，等价于
允许不可信输入在当前 Python 进程中执行代码。

本课使用 `ast.parse(expression, mode="eval")` 把字符串转换为抽象语法树，然后只解释明确
允许的节点：

| AST 节点 | 本课是否允许 | 原因 |
| --- | --- | --- |
| 数字常量 | 是 | 算术的操作数 |
| `+ - * /` | 是 | 本课定义的二元运算 |
| 一元 `+ -` | 是 | 支持 `-5`、`+(2)` |
| 括号 | 间接允许 | AST 用树的层级表达括号 |
| 函数调用 | 否 | 可能调用系统能力 |
| 属性访问 | 否 | 可能接触对象内部能力 |
| 幂、位运算 | 否 | 不属于当前工具契约，也可能造成资源问题 |
| 名称、变量 | 否 | 计算器不需要外部状态 |

白名单原则是：默认拒绝，只执行我们逐项证明安全且必要的语法。

## 4. 两类错误为什么要分开

代码中已经定义：

- `InvalidToolArguments`：参数缺失或类型错误，例如没有 `expression`；
- `UnsafeExpressionError`：参数是字符串，但包含工具不允许执行的语法。

两者分开后，后续 Agent 可以采取不同策略：参数错误可能让模型重新生成调用，安全违规则可能
触发审计或立即终止。错误类型本身就是控制策略需要的数据。

## 5. 你的实现任务

打开 `src/agent_lab/tools.py`，只实现 `CalculatorTool.run()`。推荐拆出一个私有递归方法，流程：

```text
读取 arguments["expression"]
    ↓
检查存在且为 str
    ↓
ast.parse(..., mode="eval")
    ↓
递归遍历 AST
    ├── 允许的节点：计算
    └── 其他节点：抛 UnsafeExpressionError
    ↓
把结果转换为 str 返回
```

允许的运算符仅为：

```text
+  -  *  /
```

不要使用 `eval()`、`exec()`，也不要通过字符串替换过滤危险内容。黑名单无法枚举所有 Python
语法，AST 白名单才是这里要练习的安全模式。

运行：

```bash
uv run pytest
```

完成标准是 8 个测试全部通过：第一课 3 个，加上本课 5 个。
