# 课程学习方法与工程原则

> **文档类型**：学习与工程约定  
> **导航**：[文档中心](../README.md) · [系统课程总纲](curriculum.md)

## 最终目标

我们将逐步实现一个“研究助手”：它可以理解研究问题、调用工具收集资料、保留上下文、
拆解复杂任务、让多个专职 Agent 协作，并具备预算、安全、可观测性和故障恢复能力。

重点不是堆功能，而是回答四个问题：

1. 为什么需要这个能力？
2. 它的最小抽象是什么？
3. 在失败、并发和不可信输入下，它还能否成立？
4. 什么时候值得把它拆成独立服务或换一种语言？

## 为什么不一开始复制 Shannon 三层架构

Shannon 把 Orchestrator、Agent Core 和 LLM Service 分别放在 Go、Rust、Python 中，
是生产系统对并发、隔离与模型生态的回应。但在还没有这些压力时直接拆服务，会让网络、
序列化、部署和调试成本盖过 Agent 的核心逻辑。

所以本项目遵循“单进程验证抽象，再按压力拆边界”：

```text
现在：Python 单进程
  Model -> Agent Loop -> Tool

以后：
  Go Orchestrator -> Python LLM Service
                  -> Rust Tool Runtime
```

## 每一课的完成标准

每个小阶段都应该包含：

- 一篇 `docs/` 下的概念文档；
- 一个不依赖真实网络的确定性测试；
- 一个需要你亲手实现或修改的核心练习；
- 一次代码审阅，说明正确性、边界条件和可演进性；
- 必要时再接入真实模型，避免把 API 波动误认为 Agent 逻辑问题。

## 学习原则

1. **先确定性，后智能性**：先用脚本模型测试控制流，再连接真实 LLM。
2. **模型不是控制器**：循环、预算、权限和终止条件由程序掌握。
3. **失败是一等公民**：超时、无效参数、重复执行和部分成功都要进入设计。
4. **先单体，后分布式**：只有边界被验证后，服务拆分才有价值。
5. **记录决策，不只记录结果**：文档要解释为什么这样设计。
6. **协议描述必须无歧义**：明确区分字段名和固定值；不要用斜杠串联结构。多个字段使用字段表
   或完整示例，并检查字段数量、名称、类型与代码和测试一致。

### 课程推进时的文档同步清单

开始新课或完成课程验收时，必须同时检查并按需更新：

1. 根目录 `README.md` 的当前阶段、当前课程、运行命令与文档链接；
2. `docs/README.md` 的当前学习位置、目录树和已有课程状态；
3. `docs/00-overview/curriculum.md` 的课程序号、状态、导航和文末当前学习位置；
4. 当前课程与相邻课程的状态、上一课/下一课链接；
5. 开始新课前，把上一课每一道思考题的参考答案补充到上一课文档；
6. 新增代码、测试、脚本、依赖或环境变量对应的说明。

系统总纲是完整课序的权威来源；另外两份 README 提供面向入口读者的同步摘要，不能长期落后于
总纲。

思考题答案采用延迟公开：进行中的课程只保留题目，让学习者先独立思考；切换到下一课时再把
上一课答案写回原课程文档，形成完整复盘记录。

## 课程的时效性与准确性

Agent 工程同时包含长期稳定的原则和变化很快的产品事实。课程对两者分层维护：

| 类型 | 例子 | 维护方式 |
| --- | --- | --- |
| 稳定原则 | 不信任模型输入、最小权限、有界重试 | 作为课程主干，不与某个 SDK 绑定 |
| 版本化协议 | API 字段、消息角色、MCP/JSON Schema 版本 | 记录协议和版本，用契约测试固定边界 |
| 时效快照 | 模型 ID、上下文长度、价格、功能组合 | 标注核验日期和官方链接，不在核心代码中写死 |
| 试验能力 | beta/preview 功能、新型工具 | 明确标注试验性，不作为必修主路径 |

每次进入 Provider、MCP、Skills、Desktop 或其他快速变化的阶段时，都必须：

1. 先查阅供应商或协议项目的一手文档，不以旧博客和模型记忆作为真相源；
2. 在文档中标注“最后核验日期”，并把易变数值与稳定设计原则分开；
3. 优先测试项目自己的稳定契约，真实 API 只用显式的手动或定期契约测试验证；
4. 记录 Provider、请求的模型 ID、服务端返回的模型版本（如果有）和用量，不把模型别名
   当成永不变的版本锁；
5. 当官方文档与课程冲突时，先停止实现并更新课程决策，不为了保持旧教程而适配错误前提。
