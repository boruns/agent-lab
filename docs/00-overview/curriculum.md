## 1. 学习目标

我们将从零构建一个研究助手 Agent。最终系统能够：

- 接收自然语言目标并自主选择下一步动作；
- 使用 DeepSeek 作为默认模型，OpenAI 作为备用 Provider；
- 安全地调用本地工具和 MCP 服务；
- 按需发现并加载 Skills；
- 管理上下文、会话和长期记忆；
- 规划任务、验证结果并在需要时请求人工确认；
- 使用多个专职 Agent 完成搜索、分析和写作；
- 在失败后恢复，并具备预算、权限、审计和可观测性；
- 将不可信代码或命令放进受限制的 Rust 执行环境。

这里的目标不是“会调用一个 Agent 框架”，而是理解框架内部必须解决的工程问题。完成课程
后，你应该能够阅读 Shannon、LangGraph、OpenAI Agents SDK 等实现，并判断它们的设计取舍。

## 2. 学习者假设

- 假设你会 Python、Go 和 Rust；
- 不假设你了解 Agent、Function Calling、MCP、Skills、RAG 或多 Agent；
- 每个新概念必须先解释它解决的问题，再要求你实现；
- 不把模型输出当作可信输入；
- 不把“测试通过”自动等同于“设计正确”。

## 3. 课程设计原则

### 3.1 依赖顺序

课程按下面的能力依赖推进：

```text
LLM 决策循环
    ↓
本地工具边界
    ↓
Provider 与真实 Function Calling
    ↓
MCP / Skills / Hooks 扩展机制
    ↓
上下文、状态与记忆
    ↓
规划、反思与人工介入
    ↓
评测与研究助手单体版
    ↓
多 Agent 编排
    ↓
持久化、沙箱与生产治理
    ↓
Desktop 控制面
```

后面的阶段只能使用前面已经实现并测试过的抽象。

### 3.2 两条并行主线

每一阶段同时推进两条主线：

```text
能力线：模型、工具、Skills、记忆、规划、多 Agent
控制线：测试、安全、轨迹、预算、权限、恢复、评测
```

Agent 增加一种能力时，必须同时回答：谁可以触发它、如何限制它、失败后怎么办、如何观察和
评测它。

### 3.3 先确定性，后真实模型

控制流先使用 `ScriptedModel` 测试，真实 DeepSeek 调用只作为单独的集成测试。这样测试失败时
可以区分：是 Agent 逻辑错误，还是网络、模型随机性、配额或 Provider API 问题。

### 3.4 先单体，后分布式

在 Python 单进程中验证抽象之后，才引入 Go 编排服务和 Rust 执行服务。服务拆分必须对应已
出现的并发、可靠性或安全压力，不能只为了模仿 Shannon 的目录结构。

## 6. 为什么按这个顺序安排

### Skills 放在 Provider 和 MCP 之后

Skill 是可复用的任务方法，不是可执行动作。先有真实模型和工具，才能观察 Skill 如何改变模型
选择和执行；先理解 MCP，才能明确 Skill 是“怎样完成任务”，MCP 是“怎样连接外部能力”。

### 记忆放在 Skills 之后

Skills 教会我们按需装载程序性知识；上下文与记忆阶段再把这种思想推广到历史、摘要和检索
结果。两者都消耗上下文，但生命周期和所有权不同，先区分再统一管理更清楚。

### 评测放在多 Agent 之前

多 Agent 会显著增加成本、延迟和失败面。如果没有单 Agent 基线和稳定评测集，就无法证明拆成
多个 Agent 带来了收益。

### Go 和 Rust 延后

- Python 适合模型 SDK、快速验证协议、上下文和检索；
- Go 在真正出现并发编排、背压和持久工作流时引入；
- Rust 在需要隔离不可信执行和严格资源边界时引入。

语言选择始终对应已经出现的问题，而不是为了使用多语言而拆服务。

### Desktop 放在可靠工作流与安全治理之后

Desktop 是已有 Agent 能力的控制面，不应该成为第二套 Agent 状态机。只有流式事件、取消、
人工审批、持久化恢复和权限边界稳定后，UI 才能通过清晰契约展示和控制任务。默认选择 Tauri
是为了复用 Rust 安全边界；Vue 和 Element Plus 只负责交互与展示。

## 7. 每课固定学习流程

每一课都按同一模板进行：

1. **问题**：真实系统为什么需要它；
2. **位置**：它在 Agent 数据流中的位置；
3. **模式**：框架无关的最小抽象；
4. **风险**：失败、攻击、成本和边界条件；
5. **练习**：由你实现一个小而完整的核心功能；
6. **测试**：先观察失败，再实现到通过；
7. **审阅**：检查测试没覆盖的设计缺口；
8. **集成**：把能力接回研究助手；
9. **复盘**：回答思考题并记录设计决策。

## 8. 阶段验收规则

进入下一阶段前，需要同时满足：

- 自动化测试和格式检查通过；
- 你能用自己的话解释功能存在的原因；
- 能指出至少一个失败场景和一个安全边界；
- 实现已接入阶段项目，不是孤立代码；
- `docs/` 记录概念、决策和限制；
- 涉及真实 API 时，有确定性单元测试和显式的手动集成测试；
- 新依赖、新语言或新服务都有明确引入理由。

## 9. 与 Shannon 的对应关系
